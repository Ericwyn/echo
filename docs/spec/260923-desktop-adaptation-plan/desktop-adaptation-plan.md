# Echoes 桌面端适配方案（讨论稿）

状态：设计稿与首轮实现并行维护；Linux 优先。创建：2026-09-23。

[spec 总览与阶段状态](README.md) · [产品/技术决策](decisions.md) · [统一验收矩阵](acceptance.md)

本文维护产品设计和跨阶段约束；各 phase 维护具体实施步骤与退出条件，验收状态统一记录在验收矩阵。

## 1. 目标与推荐决策

用同一份 Flutter 工程交付 Android、Linux、Windows；共享播放业务、数据访问、状态与视觉基础组件，分别组织适合触控和鼠标键盘的界面。Ubuntu 是第一桌面验收平台，Windows 独立构建并实机验收。Windows 环境缺失时可继续 Ubuntu 工作，但保留 Windows 未验收状态。

结合用户补充的参考图，建议默认形态为两种工作模式：**浏览模式：单一资料库导航 + 内容；播放模式：左侧封面/歌曲信息 + 右侧歌词或队列。两种模式共用同一条常驻底部播放条。** 播放模式在窗口内展开，默认收起资料库侧栏，返回后恢复原浏览位置。浏览时的停靠队列留作后续可选功能，第一版不同时堆叠导航、内容、队列三列。

参考图主要借鉴信息层级、专辑封面网格、播放控件位置、歌词/队列切换关系和应用内窗口导航；使用 Echoes 自己的颜色、字体、图标与现有设计 tokens，不照搬橙色主题或其他产品标识。Linux 使用 Echo 自绘顶栏并隐藏 GNOME 的 GTK 标题栏。

本轮建议以“可日常使用的桌面客户端”为目标：导航、队列、播放控制、系统媒体控制、托盘、窗口生命周期、安装包和 Android 回归一起验收。暂缓桌面悬浮歌词、均衡器、复杂全局快捷键、Flatpak/Snap 等额外功能。

## 2. 已核实的现状

| 现象 | 当前实现与原因 | 影响 |
| --- | --- | --- |
| 重复的左侧导航 | 宽屏采用统一的 EchoExpandedNavigationSidebar；宽屏不再通过 drawer 打开第二套菜单 | 桌面侧栏按用户给定的四组入口组织；手机抽屉继续复用对应目的地 |
| 桌面播放控制 | 增加固定桌面播放条，音量与进度使用同一细 scrubber 风格 | 已实现首轮布局；用户反馈音量条外观可接受，仍需在不同宽度验收 |
| 播放工作区与队列 | 左侧固定封面/歌曲信息，右侧切换歌词或队列；动态背景取自当前封面 | 已实现首轮；焦点/快捷键、长队列滚动与尺寸适配仍待验收 |
| 系统媒体控制 | Linux 通过独立 MPRIS/D-Bus adapter 发布状态和转发命令 | 用户确认 Ubuntu 控制播放且可见封面；完整 seek 与生命周期边界尚待验证 |
| 托盘与关窗策略 | 增加 tray_manager/window_manager 生命周期服务；Linux runner 已实现唯一实例和重复 activate 复用窗口 | 用户确认托盘基础功能正常；二次启动、宿主消失、关窗恢复与显式退出仍未完整验收 |
| 新增音量容易出错 | `_cancelFade`、`_fadeIn` 等多处 `setVolume(1.0)` | 仅增加滑块会导致切歌/暂停后用户音量被覆盖 |
| 音质出现 `0bit` | `_buildAudioSpecText` 对位深只检查非空 | 应把非正值视为未知，统一格式化，手机端也受益 |

复用基础已经存在：设计 tokens、`EchoSongRow`、`PlayerScrubber`、`SyncedLyricsView`、队列 entry ID 与 revision、防止拖拽期间队列变化的检查，以及 shell/player/queue 的 widget tests。

本机核查：Ubuntu 22.04.5 LTS、GNOME 42.9、X11；系统 libmpv 为 0.34.1。用户已在桌面环境确认 MPRIS 播放控制/封面和托盘基础功能。应用 release 通过本机 HTTP WAV smoke test 验证 MPV 初始化与媒体流加载不再输出 `subs-fallback`/磁盘缓存目录错误；Linux x64 release 已重新编译。CI 的 PR 主任务固定到 Ubuntu 22.04 并构建 Linux；Windows PR CI 暂缓。

## 3. 桌面交互设计

### 3.1 一个导航系统

- 左侧顶部：Echoes、当前音乐库/账号选择器、连接状态；点击账号弹出小型菜单，切换线路在锚定弹窗中完成。
- 桌面侧栏沿用用户确认的目的地分组：发现（音乐流、搜索）、资料库（全部歌曲、歌手、专辑）、个人收藏（收藏歌曲、收藏专辑、收藏歌手、我的歌单）、管理（下载管理、离线下载、设置）。
- 侧栏使用统一字号和图标行高，顶部品牌区与底部账户区属于固定 chrome；账户区域高度与桌面播放条对齐。新增页面入口时扩展这份定义，不重新放回重复的“音乐流/我的/曲库”顶层项。
- 探索入口只在对应服务可用时出现；尚未有明确页面的服务器离线导入/统计入口不放入桌面侧栏。
- 宽屏不再打开第二个左抽屉。窄屏可折叠成图标栏，全部目的地仍可访问。
- Android 保留底部主导航与账号抽屉，复用同一份目的地、可见性和操作定义。
- 设置、下载、详情在桌面 shell 的内容区导航，播放条和主导航保持稳定；登录/重新认证仍可使用独立页面。
- 手机与桌面采用不同的导航策略，共享页面、数据 provider 和播放核心。手机继续使用 `StatefulShellRoute` 的分支栈保留 Tab 状态；桌面用独立的单 Navigator，以音乐流作为固定根页面。
- 桌面侧栏切换歌曲、歌手、专辑、收藏等主目的地时替换当前主页面；页面内部打开的详情沿同一个 Navigator 入栈。这样侧栏连续切换不会制造歌曲/歌手交替的返回链，详情仍可逐层返回。
- 桌面返回最终落在音乐流根页面；根页面上的返回键不调用 Android `moveTaskToBack`。手机返回规则不变。
- 桌面顶部提供返回、前进和搜索；返回/前进与当前侧栏目的地同步。浏览页面原栈内 pop 保留页面状态；前进会按路由 builder 重建页面，滚动/筛选状态需逐页验证并补足。
- 首页将现有大横卡调整为有限尺寸的封面网格/横向专辑架：标题、歌手、明确的“查看全部”，列数随内容空间变化，左右翻页可点击。沿用“最近播放/随心听”等现有数据模块，不新增参考图中尚未支持的电台等业务。

### 3.2 常驻桌面播放条

建议高度约 88–104 个逻辑像素，跨应用底部；具体值以字体、缩放和窗口约束验收。

| 左侧 | 中间 | 右侧 |
| --- | --- | --- |
| 封面、歌名、歌手、收藏 | 随机、上一首、播放/暂停、下一首、循环；下方时间与可拖动进度 | 音量/静音、音质摘要、队列开关、正在播放入口 |

- 没有歌曲时保留紧凑空状态，控制禁用；有歌曲但暂停时保持可控。
- 歌名截断可查看完整信息，封面/标题区域可进入正在播放。
- 音量是应用音量，与系统音量独立；保存用户选择，静音后恢复原音量。
- 宽度不足按优先级收起低频信息；保留播放、切歌、进度及队列入口。
- 手机继续使用 MiniPlayer，复用歌曲信息、按钮动作、进度与背景基础组件。

### 3.3 正在播放与歌词

- 默认进入窗口内的播放工作区并收起资料库侧栏：左侧有限尺寸的封面与歌曲信息，右侧同步歌词；点击“队列”只替换右侧内容，封面和底部播放条不移动。
- 浏览中点击底部封面或歌词按钮进入歌词状态；点击队列按钮进入队列状态；关闭播放工作区/Esc 返回原浏览位置。再次点击底部当前模式按钮可收起工作区；工作区内部 tab 只切换内容。完整状态表见 [P3](phase-3-player-workspace.md)。
- 封面建议上限 320–400 个逻辑像素，歌词列限制阅读宽度，避免封面与滑杆无上限放大。
- 无歌词时呈现歌曲/专辑信息与明确空状态；加载失败可重试。
- 点歌词定位继续调用现有 seek 流程；手动滚动歌词后暂停自动跟随，提供“回到当前”操作。
- 普通播放工作区不等同于操作系统全屏；真正全屏作为可选操作，保留控制、歌词/队列切换与退出入口；Esc 先退出全屏，再返回浏览，播放不中断。
- 缩小窗口先调整列宽，再切单列或内容页签，不依靠 `width > height` 判定桌面布局。
- 页面切换和窗口缩放不得销毁播放器；动态 Hero 只在确有空间关系的场景保留，避免跨布局重复 tag。

### 3.4 队列成为可持续操作的面板

- 第一版：播放工作区右侧呈现宽列表，沿用参考图“左侧封面固定、右侧歌词/队列互换”的布局，无手机拖拽把手和模态遮罩。
- 列表按可用宽度显示序号/播放标记、封面、歌曲/歌手、专辑、时长、移除；当前项有稳定高亮，删除等动作不依赖 hover 才能发现。
- 面板包含：当前歌曲、后续队列、定位当前、拖拽排序、移除、清空后续。
- 常规歌曲列表：单击选中、双击或明确播放按钮播放；队列单击定位/选中，双击播放。当前条目使用 entry ID，重复歌曲不会被错误合并。
- 保留可点击的更多按钮，同时支持右键菜单；排序把手可见，不能只靠长按。
- 搜索/筛选队列可列入第二轮；若实现，过滤时禁用拖拽或显式映射 entry ID，不能直接按过滤索引修改原队列。
- 继续使用懒构建列表。以用户截图的 1654 首队列及 5000 首压力样本验证滚动和定位，避免复制大列表并随进度频繁重建。
- 窄窗口优先缩小或收起左侧大封面，让歌词/队列获得完整宽度，底部播放条仍可操作；手机保持底部队列面板。
- 后续可选：浏览模式下 320–360 逻辑像素的停靠队列，允许边浏览边整理；复用相同队列内容，不另外实现状态和操作。
- “播放队列”与“歌单”分别命名，避免临时播放顺序和保存的歌单混淆。

### 3.5 鼠标、键盘和密度

- 行、按钮支持 hover、焦点提示和 tooltip；滚动区域可见滚动条，操作菜单按触控/鼠标选择底部弹层或锚定菜单。
- 首轮快捷键：Space 播放/暂停、Ctrl+F 搜索、Ctrl+Left/Right 切歌、Esc 关闭当前临时界面；输入框、滑杆和弹窗优先处理自身按键。
- 硬件媒体键走系统媒体会话；不额外注册一套重复处理的全局媒体热键。
- 歌曲行的紧凑密度只作用于桌面；Android 保留足够触控面积和无障碍语义。
- Linux 隐藏 GNOME 默认标题栏和原生窗口框，绘制 Echo 桌面顶栏及可拖动边缘缩放区；保留拖动、缩放、最大化与最小化控制。Windows 暂保留原生标题栏，等 Windows 编译和实机验收后再决定是否启用共享自绘层。
- 不把 Windows/macOS 的整体文字缩小策略直接套给 Linux。先按系统缩放正常布局，再提供可选密度设置。

### 3.6 尺寸策略

结构首先由可用逻辑尺寸决定，鼠标/键盘能力影响交互，操作系统只决定原生集成。

- 延用既有 compact/medium/expanded tokens 作为起点，不全局硬改断点影响手机页面。
- 各内容组件使用实际 `LayoutBuilder` 约束；播放模式两列由封面与歌词/队列各自最小可用宽度决定。
- 后续若增加停靠队列，条件为可用宽度至少满足“导航宽度 + 当前页面最低可用宽度 + 队列宽度 + 间距”；不满足时回到播放工作区。
- 测试建议覆盖 840×560、1024×768、1280×720、1440×900、1920×1080；840×560 是 Linux/Windows 桌面下限，避免切回紧凑/中等移动式路由；Android 不受此窗口限制。
- 缩放覆盖 100%、125%、150%、200% 与大字体；尺寸为逻辑像素，不能用物理分辨率猜测字体缩放。

## 4. 代码复用与改造边界

```text
手机界面 / 桌面界面 / 系统媒体按钮 / 托盘菜单
                         ↓ 统一播放命令
PlaybackCommands + PlaybackSnapshot（先包装现有 PlayerNotifier）
                         ↓
现有队列、鉴权、线路切换、缓存、下载、播放恢复、seek 逻辑
                         ↓
just_audio → Android 后端 / 桌面 just_audio_media_kit

PlaybackSnapshot → Android AudioService / Linux MPRIS / Windows SMTC
DesktopLifecycle → 窗口、托盘、单实例、退出
```

建议新增或抽取的责任（命名为方案占位，不预先承诺整个目录重写）：

| 组件 | 责任 | 复用范围 |
| --- | --- | --- |
| `PlaybackCommands` | 播放、暂停、切歌、seek、音量、队列操作统一入口 | 全平台与所有系统入口 |
| `PlaybackSnapshot` | 当前曲目、逻辑进度、时长、播放状态、音量、可操作能力 | UI 与系统媒体适配器 |
| `AppNavigationModel` | 主/次导航、账号与线路操作、功能可见性 | Drawer、Rail、Sidebar |
| `PlaybackControls` / `TrackIdentity` | 纯组件与语义、按钮状态 | MiniPlayer、DesktopPlayerBar、手机全屏播放 |
| `PlaybackQueueContent` | 列表、定位、排序、条目动作，不调用 Navigator 关闭容器 | 手机 Sheet、桌面播放工作区、后续 Dock |
| `SongAction` + presenters | 共用动作和权限，分别呈现底部菜单/右键菜单 | 所有列表与队列 |
| `DesktopMediaSession` | 发布系统状态、接收系统命令 | Linux/Windows 实现，共用契约 |
| `DesktopLifecycleService` | 窗口状态、托盘、单实例、退出流程 | Linux/Windows |

关键约束：

1. 只有一个播放状态源、一个有效播放器所有者。系统适配器不再创建播放器；不能调用 handler→controller→同一 handler 形成命令循环。
2. 先给现有 `PlayerNotifier` 加边界；它已有约 4200 行，不在桌面改造中同时重写播放恢复和缓存机制。
3. `initAudioService` 当前负责创建播放器，Android 迁移时需要明确所有权；首轮可保留 Android 初始化路径，通过公共命令/快照接入，而非一次改动全部生命周期。
4. 音量统一为 `effectiveVolume = muted ? 0 : userVolume * fadeGain`；淡入淡出只改变 fadeGain。移除散落的 100% 重置，系统与 UI 都写 userVolume。
5. 适配器订阅在退出或播放器更换时解除；切换音乐库不得留下旧的系统会话或旧回调。
6. 系统媒体会话异常独立降级并可重试，不阻塞首次播放。共享页面不直接依赖托盘、窗口或 D-Bus 插件。
7. 复用业务和组件，容许手机与桌面有不同编排 Widget；不以强行共享完整页面作为复用率目标。

2026-09-23 补充：[音流技术文章调研](research-stream-music.md) 支持沿用现有播放后端、独立接入系统会话的方向。P1 需把当前依赖 `_audioHandler` 的元数据构建抽离；唯一播放器约束针对实际音频引擎，SMTC 所需的无音源原生会话宿主可以由平台 adapter 单独管理。

主要修改入口：`lib/widgets/echo_app_shell/`、`main_scaffold.dart`、`app_drawer.dart`、实际 router 配置、`lib/features/player/`、`player_provider.dart`、`audio_handler_service.dart`、桌面 runner 与 CI。先抽取队列内容，再替换容器，可最大限度复用已有 tests。

## 5. 系统媒体控制、托盘与 Ubuntu 兼容

### 5.1 系统媒体会话

Linux 通过 MPRIS/D-Bus 暴露歌曲标题、歌手、封面、状态、进度和控制；桌面环境决定媒体卡片具体出现在哪个系统区域。Windows 对应 SMTC。系统媒体控制与托盘是独立能力，MPRIS 不依赖 AppIndicator。[MPRIS 规范](https://specifications.freedesktop.org/mpris/latest/)、[Windows 适配候选](https://pub.dev/packages/audio_service_win)。

选型建议：优先验证与当前 `audio_service` 共用接口的 `audio_service_mpris` 和 `audio_service_win`，但在验证通过前只列为候选。Linux 稳定版文档列出了 `Seek`、`Seeked`、音量、Raise 等缺口，不能把“加依赖”当成完整实现；若这些缺口无法在固定版本中补齐，Linux 使用基于 `dbus` 的小型 MPRIS 适配器，共享命令/快照接口不变。[功能清单](https://pub.dev/packages/audio_service_mpris)

首轮系统控制验收包含播放/暂停、上一首/下一首、元数据、准确状态；公开声明完整 MPRIS seek 前，必须验证绝对定位、相对 seek、Seeked 信号与能力字段。未支持的功能如 TrackList/OpenUri 不冒充支持。Windows 在对应实机上验证，编译通过不足以代替 SMTC 验收。

Windows 的 K3 比较范围补充为现成包（`audio_service_win`、`smtc_windows`）与薄 C++/WinRT adapter；Rust/FRB 根据已证实的缺口再选择。公开示例用于理解接口，最终实现仍需包含事件释放、错误隔离、封面清理与时间轴；不会把整包 fork、Melos 或播放引擎迁移作为本次前置要求。具体见 [P0-B](phase-0-platform-spike.md) 与 [P4](phase-4-system-integration.md)。

同步要求：

- 系统命令全部调用现有业务入口，保持随机、循环、转码 seek 与网络恢复语义一致。
- 发布逻辑播放位置，复用现有转码 offset 处理；按状态变化/seek/低频校正更新，避免逐帧广播 D-Bus。
- 每次播放条目使用稳定、合法的媒体标识；重复歌曲以 queue entry ID 区分。
- 认证封面由应用解析并缓存为系统可读取的本地文件，异步结果校验曲目版本；不把带 token/API Key 的 URL直接暴露给系统。
- 切换库、退出、清空当前项时清理元数据；系统显示与 UI/实际播放器状态保持一致。

### 5.2 托盘与窗口

已锁定 `tray_manager 0.5.3` 与 `window_manager 0.5.2`，使用 Flutter 3.41.7；Ubuntu 22.04 release 编译通过，用户确认托盘基础功能正常。扩展到其他 GNOME/Wayland 组合前仍需复验宿主、恢复行为与 native 依赖。插件页面中的更新版本要求高于本项目当前 Flutter 工具链，因此仍固定版本、不追随 latest。[tray_manager](https://pub.dev/packages/tray_manager/versions/0.5.3)、[window_manager](https://pub.dev/packages/window_manager/versions/0.5.2)

- 托盘菜单：显示主窗口、播放/暂停、上一首、下一首、退出；曲目摘要随切歌更新。
- Linux 不依赖单击/双击托盘图标才能恢复窗口，菜单中必须有明确的“显示主窗口”。
- 默认建议：托盘可用时，关闭按钮隐藏窗口并继续播放；首次告知且可在设置改为退出。
- 托盘不可用或宿主消失时，回退为最小化到任务栏并保留恢复入口；不能关成一个无法找回的隐藏进程。
- 托盘“退出”和应用退出命令真正停止播放、保存会话、释放 D-Bus/托盘后结束进程；下载进行中按 [D6](decisions.md) 提供取消退出或停止任务并退出；不承诺尚未支持的断点恢复。
- 单实例：再次启动聚焦/恢复已有窗口，不创建第二个播放器。Linux 已从 `NON_UNIQUE` 切换到默认唯一实例，并在 activate 时呈现已存在窗口；仍需桌面实测。Windows 使用对应单实例机制。
- 保存窗口大小、最大化状态，恢复时处理显示器移除；Wayland 不保证任意绝对定位或强制抢焦点成功，能力不足时尊重窗口管理器。
- 首轮不默认开机启动，后续可选。

GNOME 的托盘显示需要 AppIndicator/StatusNotifier 宿主。你本机已安装并配置启用 AppIndicator，预计可直接验收；仍要验证实际显示与宿主重启。其他 Ubuntu/GNOME 环境若缺扩展，应用说明原因并回退，不在后台更改系统扩展。[GNOME 扩展](https://extensions.gnome.org/extension/615/appindicator-support/)

### 5.3 安装与原生依赖

- Linux 第一交付提供 Ubuntu `.deb` 与完整 bundle 压缩包；安装应用图标、`.desktop`、分类和一致应用 ID/MPRIS DesktopEntry，保持 Dock 中图标归组和单实例激活一致。
- 在 Ubuntu 22.04 基线上固定构建工具链和 CI runner；后续增加 24.04 与 Wayland 验收。当前 PR 主任务使用 `ubuntu-22.04`，不添加 Windows 构建 job，Windows release workflow 不作为此阶段门槛。
- 构建环境补齐 clang/lld、GTK、CMake、Ninja、pkg-config 等；托盘 native 依赖按最终锁定版本列出。上一轮构建的临时 linker shim 仅用于验证，正式 CI 应配置完整工具链。
- 运行时单独核查 libmpv、GTK、托盘依赖与字体。`ldd` 主程序正常不代表通过动态加载的 libmpv 可用；必须在干净机器做实际音频播放。
- `.deb` 声明依赖，bundle 文档说明依赖；打包 libmpv 时明确编解码能力、许可证及分发责任。
- Windows 同时交付可运行 release bundle/安装包，验证封面文件路径、非 ASCII 用户目录、托盘资源与 SMTC。

## 7. 验收与完成定义

[统一验收矩阵](acceptance.md) 将需求映射为 A01–A15，并列明平台、窗口、缩放、输入、播放数据、端到端脚本和证据格式。各 phase 引用相同编号，不重复维护另一份结果表。

完成包含三种不同证据：共享逻辑/widget 回归、目标平台真实系统交互、干净环境安装和实际播放。编译成功不能替代后两项。Windows 没有实际桌面证据时标为未测，并限制发布声明；不得阻塞已经可以验证的 Ubuntu 界面与共享工作。

## 8. 可以顺带改善的移动端体验

首版共享改动：音质未知值不显示 `0bit`；播放队列与歌单术语统一；歌词手动浏览后提供“回到当前”；“清空后续”与“清空全部”明确区分。移除撤销列为后续优化，首版不因此扩大队列状态改造。

保留手机的底部导航、MiniPlayer、触控队列面板与完整播放页。共享歌曲动作与队列内容后，可分别调整触控尺寸和桌面密度。Android 平板/横屏根据真实空间受益于自适应编排，不简单强制套用桌面鼠标操作。

## 9. 决策状态与首版边界

用户明确要求、推荐交互和技术选型分别记录在 [决策文档](decisions.md)：R1–R5 为用户需求，D1–D8 为待确认的默认值，T1–T6 为实施约束，K1–K6 在 P0 回填证据。
