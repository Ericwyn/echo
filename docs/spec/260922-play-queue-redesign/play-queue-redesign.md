# 播放队列排序、状态展示与随机播放技术方案

日期：2026-09-22。状态：已实施；Android 真机体验待验收。

## 1. 目标与已确认行为

队列显示顺序就是实际播放顺序；用户能拖动调整顺序，并区分当前位置之前、当前、后续三个区域。

已确认：开启随机只打乱当前歌曲之后的条目；关闭随机时，**整个队列恢复基础顺序**，当前歌曲与播放进度保持不变。恢复时不得复活已删除条目。灰色表示“当前位置之前”，不表示歌曲实际听过或听完。

示例：

```text
基础顺序： A B C D E F G
开启随机： A B [C] F D G E
播放到 G： A B C F D [G] E
关闭随机： A B C D E F [G]
```

关闭随机后，E 即使尚未听过，也因位于当前歌曲之前而变灰；下一首回绕到 A。

基础顺序是持续维护的队列，不是创建时永不改变的快照：非随机模式拖动更新基础顺序，随机模式拖动只改变实际顺序；新增、删除同步作用于两套顺序。这些操作仅作用于播放队列，不修改来源歌单。

下文关于跨轮上一首、删除当前歌曲和清空后续的规则，是本方案建议的默认值，用于补齐尚未逐项讨论的边界。

## 3. 数据结构与不变量

建议新增不可变的 PlaybackQueueState，作为 PlayerState 的组成部分：

```dart
class QueueEntry {
  final String entryId; // 每次入队生成；同歌多次入队拥有不同 ID
  final Song song;
}

class PlaybackQueueState {
  final Map<String, QueueEntry> entries;
  final List<String> baseOrder;
  final List<String> playOrder;
  final String? currentEntryId;
  final int revision; // 队列结构或排列改变时增加
}
```

以上为结构示意，不是直接可编译代码。entryId 可以复用项目已有 uuid 依赖；生成器可注入测试。revision 仅用于运行时并发保护，无须持久化。

PlayerState 保留一个权威 PlaybackMode；shuffleEnabled、loopMode 等兼容读取值由模式派生，原生循环策略单独计算。避免 mode、shuffleEnabled、loopMode 被多条写入路径改成不同状态。

约束：

1. entries、baseOrder、playOrder 的条目 ID 集合相等；两个顺序内部各 ID 恰好出现一次。
2. currentEntryId 为 null 或现存条目 ID。
3. 非随机模式下 playOrder 与 baseOrder 相同。
4. currentIndex 从 currentEntryId 在 playOrder 中的位置派生；没有当前条目时为 -1，不默认高亮第一行。
5. currentSong 从当前条目派生；元数据更新保留 entryId。
6. 对外兼容的 queue 读取视图按 playOrder 映射为 List<Song>；仅队列数据变化时重建，不能每次进度 tick 创建新列表。

同歌多次入队应独立拖动、删除、高亮。收藏等歌曲级数据按歌曲身份更新相关条目；试听 URL 解析等播放请求结果按 entryId 更新目标条目。歌曲身份仍沿用项目现有音乐库作用域，entryId 不取代媒体文件或缓存的歌曲 ID。

新增 QueueReducer 或等价纯逻辑类，集中维护上述不变量。它接受状态和操作，返回新队列状态；不调用播放器、存储或 UI。PlayerNotifier 负责执行音频和持久化副作用。

## 4. 队列操作规范

| 操作 | 实际顺序 playOrder | 基础顺序 baseOrder | 当前播放 |
| --- | --- | --- | --- |
| 从歌单/专辑开始播放 | 创建新条目；随机模式下保留起播项及前缀，打乱其后缀 | 使用传入歌曲顺序 | 播放指定条目 |
| 单曲直接播放 | 新建单条目队列 | 同步 | 播放该条目 |
| 非随机模式拖动 | 移动条目 | 同步为新实际顺序 | 当前 ID 和进度不变 |
| 随机模式拖动 | 移动条目 | 不变 | 当前 ID 和进度不变 |
| 加入队列 | 追加新条目 | 追加相同新条目 | 不变；无当前条目时不自动播放 |
| 下一首播放 | 在当前条目后插入新条目 | 在基础顺序中的当前条目后插入 | 不变；无当前条目时直接播放新条目 |
| 删除非当前项 | 删除指定 ID | 删除同一 ID | 不变 |
| 删除当前项 | 删除指定 ID | 删除同一 ID | 停播、清空当前身份和进度；保留其他条目待用户选择 |
| 清空后续队列 | 删除当前条目之后的所有 ID | 删除这些相同 ID | 保留前缀、当前条目与进度 |
| 清空后续且无当前项 | 清空全部条目 | 清空 | 停止 |
| 点击队列条目 | 顺序不变 | 不变 | 切到目标 ID，从头播放，沿用现有选择行为 |

“下一首播放”在随机时也同步插入基础顺序中当前条目后，保证关闭随机后仍紧随当前条目。多次执行时，最后一次插入的条目最先播放，保持现有插入行为。对已存在的同歌仍创建新条目，不隐式移动或去重。

删除当前项沿用现有“停止”意图，本次不额外引入自动切歌；若有待完成的加载，同时使该请求失效。停止后没有任何一行高亮，也没有基于不存在游标的灰色前缀。

现有“清空后续队列”实际会只保留当前歌曲，也会删除前面的歌曲。本方案建议按按钮字面含义改为只删除实际后缀；保留的前缀仍参与后续循环。若希望沿用只保留当前歌曲的行为，应将按钮改名为“清空其他曲目”，不能保留文案与行为不一致的状态。

建议内部接口以 ID 为主：replaceQueue、moveEntry(entryId, beforeEntryId)、appendEntries、insertNext、removeEntry、clearUpcoming、selectEntry。beforeEntryId 为 null 表示尾部。UI 的索引拖动事件只在适配层转换为目标锚点，避免向下移动时索引偏移处理散落在各处。

## 5. 随机、循环与导航

### 5.1 模式转换

| 转换 | 排列处理 |
| --- | --- |
| 列表循环/单曲循环 → 随机 | 当前及前缀不动，对后缀做一次 Fisher–Yates 洗牌 |
| 随机 → 列表循环 | playOrder 完整恢复 baseOrder；按 currentEntryId 派生新索引 |
| 随机 → 单曲循环 | 同样退出随机并完整恢复基础顺序，然后重复当前歌曲 |
| 列表循环 ↔ 单曲循环 | 队列顺序不变 |
| 重复设置相同模式 | 幂等，不重新洗牌 |

无当前条目时开启随机，对整个实际队列洗牌。后缀长度为 0 或 1 时排列不变。模式切换只改变状态和原生循环设置，不调用加载当前音源的流程。

模式为随机时，替换成一个新队列要对新队列后缀洗牌；恢复持久化队列则直接安装已保存的排列，不能再次洗牌。两种入口必须区分。

### 5.2 下一首与轮次

当前轮内统一按 playOrder 前进。普通列表末尾回绕到第一个条目；随机模式末尾生成下一轮完整随机排列，再选择新排列第一项。生成与选择作为一次队列事务提交。

新轮包括所有仍存在的条目，每个条目恰好出现一次；有不同歌曲可选时，约束新轮首曲不等于上一轮末曲的歌曲身份。可先从不同歌曲的条目中随机选择首项，再洗牌剩余条目，避免反复洗牌重试。

重复入队的同歌是不同条目，仍可能在同一轮播放多次；不做全局歌曲去重。一轮不重复条目的保证仅适用于自然顺序推进，用户主动点击、回退或重新排列后可能重听。

单条目队列继续重复该曲。进入新轮时，灰色状态重新按新游标计算。

### 5.3 上一首与单曲循环

建议上一首始终选择实际列表中的前一项，位于首项时回绕到当前排列末项，且不触发洗牌。跨轮不恢复上一轮历史排列。因此在随机新轮的第一首点击上一首，会去当前新排列的最后一首，不保证回到上一轮刚播放的歌曲。此规则优先保证“所见顺序即导航顺序”。

采用这一规则后，可删除旧随机前进/后退栈与 shuffleHistoryCount；不再宣称上一首是严格收听历史。

单曲循环只影响自动完成事件；手动上一首、下一首仍沿队列移动，保持当前实现的交互。原生 LoopMode.one 的启用继续服从现有完整音源、转码 timeOffset、试听等限制。

## 6. UI 与拖动手势

队列每行从左至右：独立拖动手柄、封面和歌曲信息、更多按钮。使用 Flutter 的可重排列表能力，沿用底部面板提供的滚动控制器；具体控件参数在实施时按项目 SDK 核对，不引入新的第三方拖动库。

- 仅长按左侧手柄发起拖动；行点击播放、行长按菜单、右侧更多按钮保持各自职责。
- 用 entryId 作为稳定 key。拖动中展示抬升与占位动画，触及边缘时自动滚动；松手后一次提交顺序。
- 拖动期间记录队列 revision。若发生删除、外部排序、模式变化或换轮等结构变化，取消旧拖动，展示最新队列，避免旧索引落到另一首歌。单纯播放游标变化不必取消，提交时以最新当前 ID 派生状态。
- 排序期间播放器持续播放，不暂停、seek 或换源。
- 增加供辅助功能使用的“上移/下移”动作，首尾动作按边界禁用。

建议新增队列专用 PlayQueueRow，复用现有歌曲信息展示；公共 EchoSongRow 只按需增加可选展示参数，默认样式不变。

| 状态 | 样式与语义 |
| --- | --- |
| 当前之前 | 降低文字强调程度，保持可读；标识为“当前之前”，不标“已听完” |
| 当前 | 主题色标题、浅色背景、当前标识；正在播放/已暂停/加载中按真实状态区分 |
| 当前之后 | 普通样式，可标识为“待播” |
| 无当前条目 | 全部普通样式，不显示虚假的当前序号 |

淡化使用设计系统颜色，不对整行统一降低透明度，以免操作按钮也变得难以识别。不能只依赖颜色，当前状态同时有图标和可访问性文案。

面板首次打开后定位当前项；用户主动滚动后不随每次切歌强制抢回位置，可增加“定位当前”入口。200% 字号下允许可变行高，不能用固定行高乘索引估算位置；实施时使用能确保目标项构建的定位方案。模式整体恢复时保持当前条目可定位，拖动和手动浏览期间不自动跳动。

顶部显示“共 N 首 · 当前第 M 首 · 后续 K 首”；无当前项时只显示总数。Provider 的选择订阅增加播放、加载、模式等必要状态，不订阅每个播放进度 tick。

## 7. 播放器接入与异步一致性

### 7.1 区分新建队列与播放已有条目

目前 next、恢复重试、试听、外部播放等路径都可能调用 playSong(song, queue, index)，其中切歌经过 await 淡出等操作后才写入携带的队列快照。新设计必须拆分：

- 外部入口负责一次性建立或替换队列。
- 内部 playEntry(entryId) 只切换当前条目并加载音源，不重建队列。
- 网络恢复、音质切换、试听解析和转码 seek 复用既有 entryId。
- 保留 playSong/playQueue 的外部兼容入口，内部统一委托；不再靠歌曲列表是否相等推断是新会话还是内部切歌。

所有队列编辑同步提交一个不可变状态。异步音源请求持有播放请求 generation、entryId 与队列会话身份；await 后重新核验请求和条目有效性，只合并结果到最新状态，绝不写回旧队列快照。排序不取消同一条目的合法加载；删除目标或新建队列必须使旧加载失效。新建队列每次生成全新的条目 ID，辅助识别旧会话请求。

完成事件沿用现有 source/playback generation 保护，并补足当前条目身份检查；不能只比较 songId，否则同一首歌连续两次入队时可能误接收旧完成事件。已解析的试听结果若目标条目已删除，直接丢弃，不再次插回队列。

PlayerState 现有 copyWith 对可空字段使用 `value ?? oldValue`，不能显式清空 currentSong 等值。本次应对相关可空字段使用 sentinel/显式清空方法，或由 currentEntryId 派生消除冗余；同时检查音质、播放来源等清空路径。

### 7.2 单一模式控制入口

setPlaybackMode 作为权威入口，旧 setShuffleEnabled/setLoopMode/toggle 方法删除未使用项或委托到它。应用不再依赖底层 shuffleModeEnabledStream 写回业务模式，底层随机保持关闭；否则延迟的引擎事件可能覆盖应用队列状态。删除旧 forcedNext 标记，“下一首播放”由队列中的真实插入位置表达。

### 7.3 后台与预缓存

通知栏、锁屏、耳机上一首/下一首继续调用同一个 PlayerNotifier，不建立另一套随机算法。

提供无副作用的 peekNextEntry 供预缓存使用：普通循环可返回回绕目标；随机模式当前轮内返回下一项，轮末因下一轮尚未生成而返回空。查询不得消耗随机数或偷偷生成新轮。单曲循环不预缓存未被自动播放的相邻项。

调整顺序、增删或切模式后，若下一首目标改变，取消旧预缓存并重新评估。现有 `_precacheStartedSession` 需要同时考虑下一条目/目标版本，否则同一首播放期间拖动队列后不会重新预缓存。已满足的缓冲阈值与下载大小、平台、试听等限制继续保留。

## 8. 持久化与旧版本迁移

建议 v2 会话在同一份 JSON 中保存：

```json
{
  "version": 2,
  "mode": "shuffle",
  "entries": [
    {"entryId": "q-a", "song": {"id": "A"}},
    {"entryId": "q-b", "song": {"id": "B"}}
  ],
  "baseOrder": ["q-a", "q-b"],
  "playOrder": ["q-b", "q-a"],
  "currentEntryId": "q-b",
  "positionMs": 35000,
  "isPlaying": true,
  "updatedAt": "示意：使用现有时间戳格式"
}
```

歌曲 JSON 在真实实现中沿用完整 Song.toJson，上述仅展示结构。

建议新增 v2 存储键：优先读取有效 v2，无可用 v2 时尝试有效 v1。v1 每个列表位置分配独立 ID，初始基础与实际顺序均使用旧 queue，当前项优先按合法旧索引匹配，再回退歌曲 ID。旧随机模式没有保存实际随机排列，因此首次迁移时保留当前与前缀，对后缀洗牌一次；成功保存后仅按 v2 恢复，不重复洗牌。

v2 优先采用会话内模式，独立模式设置只用于无会话启动和 v1 迁移。恢复时直接安装保存的模式和排列，而不是调用会洗牌的普通模式切换入口。继续沿用当前恢复后暂停的行为。

写入有效 v2 成功后删除 v1；清空会话时清除新旧键，避免清空后回退到旧队列。基础顺序引用损坏时，只在 v2 中的现存条目集合内修复：过滤未知/重复 ID，补齐遗漏 ID；当前 ID 丢失则恢复为无当前、暂停，不猜测重复歌曲中的某一项。未能解码的条目从所有排列移除。若 v2 整体不可恢复且仍有 v1 才进行 v1 回退。

拖动结束、增删、模式和当前项变化后立即请求保存，进度继续按现有节流策略保存。写入执行串行化并带 dirty 标记：保存期间若又发生变化，完成后再次保存最新快照。不能像当前仅用 `_isPersistingPlaybackSession` 返回而吞掉最后一次队列修改。异步写失败记录错误并保留待重试状态，不回滚正在播放的队列，也不无限循环重试。

## 9. 实施顺序与文件范围

1. 新增条目模型、队列状态、纯操作逻辑和 v2 编解码；先验证不变量与模式转换。
2. PlayerState/PlayerNotifier 接入，迁移所有内部切歌、试听、恢复和元数据回写路径；替换随机算法，移除旧历史与强制下一首逻辑。
3. 接入持久化迁移、后台导航、预缓存失效逻辑；保留现有播放可靠性保护。
4. 新增队列专用行和拖动交互、状态展示、当前项定位；更新测试替身与页面测试。
5. 执行定向回归和真机验收；更新播放可靠性文档中“随机队列跳过预缓存”等过时描述。

新增文件建议：`lib/providers/player/playback_queue_state.dart`、`playback_queue_reducer.dart`、`playback_session_codec.dart`，以及 `lib/features/player/widgets/play_queue_row.dart`。这些名称是建议，最终可按现有目录风格调整。避免把全部新逻辑继续堆进已较大的 player_provider.dart。

本次不增加独立历史播放页、来源歌单编辑、歌曲去重、随机权重或后台服务架构迁移。

## 10. 验证与验收

| 层次 | 重点场景与断言 |
| --- | --- |
| 队列纯逻辑 | 任意增删移动后 ID 集合一致、排列无重复 ID、当前引用有效；随机只改变后缀；模式恢复等于基础顺序 |
| 重复歌曲 | 相同 songId 的两条目独立拖动/删除；恢复和重启后仍高亮同一个 entryId |
| 恢复顺序 | 删除 E 后关闭随机不恢复 E；普通拖动更新基础顺序；随机拖动在关闭随机后撤销；新增与下一首插入位置符合规范 |
| 循环边界 | 空队列、单项、两项、后缀不足两项、末尾开启随机、跨轮上一首、避免轮边界同歌重复、单曲循环手动切歌 |
| 音频副作用 | 拖动/切模式不调用重新加载当前源，不 seek 到零；切模式只按需要更新原生循环 |
| 并发 | 淡出或加载期间排序不被旧快照覆盖；删除加载目标后旧结果失效；同歌不同条目旧 completed 不误切歌 |
| 试听与恢复 | 试听 URL 更新保留 ID；已删除条目不被解析结果插回；断流重试、音质切换、转码 seek 保持身份 |
| 持久化 | v1 迁移、v2 精确恢复且不再洗牌、重复 ID/未知引用修复、无当前队列保存、写入中再次编辑后最终快照正确、清空不复活 v1 |
| 预缓存 | 下一首与实际队列一致；拖动后旧预缓存失效；随机轮末不提前洗牌 |
| UI | 三种位置样式、暂停与加载状态、手柄与行点击互不干扰、拖动越过当前项、边缘滚动、结构变化取消拖动、首次定位当前 |
| 可访问性 | 200% 字号无溢出、深浅主题、弱化文字可读、上移/下移与当前状态可被辅助功能识别 |
| Android 真机 | 播放中持续拖动不打断声音；锁屏/耳机切歌与队列一致；退出重启后排列一致且暂停；后台曲尾换轮正常 |

随机测试注入可控随机源，检查排列与边界约束，不依赖“随机结果一定不同于原顺序”这种不成立的断言。属性测试或多组操作序列用于覆盖队列不变量。

自动检查包括格式、静态分析、新队列单元测试、现有 player_recovery/preview_playback_queue/play_queue_sheet/audio_handler_service 等定向回归，以及一次全量 Flutter 测试。真机音频连续性、系统服务和手势体验仍需单独验收。
